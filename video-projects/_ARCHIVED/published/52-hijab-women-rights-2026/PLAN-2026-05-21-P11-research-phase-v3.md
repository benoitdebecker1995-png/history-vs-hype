## 0. What the self-grill caught (v2 → v3 deltas)

The self-grill ran the v2 sub-task specs against the actual files Sonnet would edit. Three structural issues surfaced; all three required revision.

### Issue 1 — v2's "Phase 2 step" doesn't exist in `/research`

v2 P11.2 said: *"Add a new step in research.md titled 'NotebookLM Angle-Discovery Pass' that runs as part of Phase 2."*

**The actual file shows:** `/research` has no formal Phase 2 step. The workflow ends at Step 9 ("Report and Next Steps") with the user being told to "Load sources into NotebookLM and verify claims" *outside* `/research`. Phase 2 verification happens via the `--apply-review` flow, not as a step inside the main workflow.

**v3 fix:** P11.2 reframes from "new Phase 2 step" to **extension of the existing `--apply-review` flow**. Angle-discovery queries run when NLM output is being ingested, which is the natural trigger point.

### Issue 2 — v2's viability gate has a chicken-and-egg sequencing problem

v2 P11.1 said: *"Mechanism-word NLM-confidence check runs at the viability gate (between Phase 1 and Phase 2)."*

**The actual file shows:** NotebookLM sources don't get into the notebook until *after* Step 8 (source list creation) and the user manually uploads them. The viability gate, sitting after Phase 1 brief, has no notebook to query for mechanism-word confidence.

**v3 fix:** P11.1 splits into two gates:
- **P11.1a — Topic Viability Gate** (runs at Phase 1, before NLM source list creation): three checks that don't need the notebook (T-tier accessibility from brief's source table, specificity-bomb count from brief's claims, thesis-discipline pre-check). Verdict: PROCEED / SHARPEN / DEFER on viability *as observable from the brief*.
- **P11.1b — Mechanism-Word Lock Gate** (runs after first NLM ingestion via `--apply-review`): the fourth check that DOES need the notebook (mechanism-word NLM-confidence). Verdict: confirm mechanism-word candidates ground HIGH or trigger soften/swap.

This matches the existing `/research` workflow's actual sequencing.

### Issue 3 — v2's "SOURCE ACQUISITION QUEUE" partially duplicates existing artifacts

v2 P11.3 said: *"Add SOURCE ACQUISITION QUEUE section to `01-VERIFIED-RESEARCH.md` template."*

**The actual file shows:** Each project already has `_research/00-NOTEBOOKLM-SOURCE-LIST.md` (generated by `tools/notebooklm_bridge.py`) that lists primary + academic + supplementary sources to acquire. Adding a parallel queue section in `01-VERIFIED-RESEARCH.md` duplicates content.

**v3 fix:** P11.3 creates a NEW per-project file `SOURCE-ACQUISITION-QUEUE.md` (parallel to the existing `00-NOTEBOOKLM-SOURCE-LIST.md`). The queue tracks **tier-upgrade actions** specifically — what to acquire to move a T3 claim to T2 or T1. The source list tracks *what sources exist* for the topic; the queue tracks *what acquisition unblocks specific claim upgrades*. Different shapes; both useful.

### Additional grill findings (smaller)

- **Bypass mechanism missing.** The existing demand-validation gate has explicit `DEMAND_OVERRIDE: true` behavior. v2's viability gates had no override. v3 adds `VIABILITY_OVERRIDE: true` to both P11.1a and P11.1b.
- **Threshold defensibility.** T3-only >30% and ≥3 specificity-bombs are educated guesses, not measured. v3 marks them as "v1 calibration — re-evaluate after 3 videos run through the gate."
- **Differentiation from `/greenlight`.** v2 didn't make the boundary explicit. v3 states clearly: `/greenlight` = will-it-get-clicks (packaging viability); P11.1 = can-we-research-it (substantive viability). They run in parallel, not redundantly.
- **Differentiation from Step 1c title pre-generation.** Step 1c brainstorms title candidates via Ollama (packaging layer). P11.2 angle-discovery surfaces hook quotes + thesis verbs + closing payoffs from NLM (content layer). No overlap; v3 names the distinction explicitly.

## 2. P11.1a — Topic Viability Gate (Phase 1)

**File to edit:** `D:\History vs Hype\.claude\commands\research.md`

**Insertion point (validated against the actual file):** Between Step 6 ("Conduct Additional Preliminary Research") and Step 7 ("Competitive Intelligence Check"). Brief from Step 5 is the input. Step 7's competitor + technique selection runs only after viability is confirmed.

**Behavior the section must specify:**

1. **Trigger condition.** Fires once per topic after the Phase 1 wiki-researcher brief is complete (Step 5 output: `_research/00-PRELIMINARY-BRIEF.md`). Cannot be skipped — `/research` cannot proceed to Step 7 without a verdict.

2. **Three viability checks** (mechanism-word check is deferred to P11.1b due to sequencing — see §0 Issue 2):

   **a. Primary-source accessibility map (T-tier projection).** From the brief's "Academic Sources" table and "Claims" section, project a T-tier distribution:
   - T1-projected: count of claims with a primary document plausibly accessible (digitized, in a verifiable language per `user-languages.md` — French/Spanish/German/Latin/Greek/Dutch).
   - T2-projected: count of claims where the primary exists but only via Anglophone scholar quotation.
   - T3-only: count of claims where only scholarly interpretation is available.
   - **DEFER threshold (v1 calibration):** T3-only > 30% of load-bearing claims, AND the inaccessible primaries are in a language the channel can't verify.
   - **SHARPEN threshold:** T3-only between 15-30%, OR T3-only > 30% but primaries are in verifiable languages (acquisition is feasible).
   - **PROCEED threshold:** T3-only < 15%.

   **b. Specificity-bomb count.** Per niche-wide data (5.4x retention lift), the topic needs ≥3 specificity bombs available — specific named documents + dates + figures + concrete factual claims. Source from brief's Claims section and Wikipedia's primary-source references.
   - **DEFER threshold:** <2 specificity bombs identifiable from brief.
   - **SHARPEN threshold:** 2 specificity bombs — possibly enough but thin.
   - **PROCEED threshold:** ≥3 specificity bombs identifiable, each with a credible source path.

   **c. Thesis-discipline pre-check.** Per `THESIS-DISCIPLINE.md`, attempt to draft a ≤12-word throughline from the brief.
   - **DEFER threshold:** No throughline forms; the brief reads as a fact-list without a sharp claim.
   - **SHARPEN threshold:** Throughline forms but feels generic / could apply to other topics.
   - **PROCEED threshold:** Throughline forms with a specific action verb that names what historical actors did.

3. **Verdict logic.**
   - **PROCEED** — All three checks PROCEED. Topic is substantively viable. Continue to Step 7.
   - **SHARPEN** — One or two checks at SHARPEN, none at DEFER. Output a specific punch-list of what's missing. Topic stays in the project folder; user iterates and re-runs gate.
   - **DEFER** — One or more checks at DEFER. Topic is not viable at the channel's current standard. Output a deferral note (what would need to change). Move to `channel-data/TOPIC-PIPELINE.md` backlog.

4. **Override mechanism.** If user explicitly overrides DEFER:
   ```
   I understand this topic is at the channel's substantive-viability ceiling.
   I am proceeding with VIABILITY_OVERRIDE: true.
   Reason: [user-supplied rationale]
   ```
   Log to `PROJECT-STATUS.md` as `VIABILITY_OVERRIDE: true` with the user's reason. The override is honest — it doesn't pretend the topic is viable; it acknowledges acceptance of the risk.

5. **Output: `RESEARCH-VIABILITY.md` in the project folder.** Single file with:
   - The three check results with evidence
   - The verdict (PROCEED / SHARPEN / DEFER)
   - If SHARPEN: punch-list of what's missing
   - If DEFER: deferral note + acquisition queue trigger to P11.3
   - If overridden: VIABILITY_OVERRIDE flag and reason
   - Mechanism-word candidates list (passed forward to P11.1b after NLM ingestion)
   - Signed-off date

6. **Gate behavior.** `/research` cannot enter Step 7 (Competitive Intelligence) until `RESEARCH-VIABILITY.md` shows verdict PROCEED or VIABILITY_OVERRIDE: true.

**Cross-reference at top of section:**
> "Companion to `/greenlight` (packaging viability — will it get clicks). This gate covers substantive viability — can we research it at the channel's standard. See `feedback-auditors-edge.md` §'tier-vibe' for T-tier accessibility, `feedback-topic-vs-angle-ordering.md` for the angle-locks-at-research principle, and `THESIS-DISCIPLINE.md` for throughline drafting."

**Acceptance:** After the edit, a fresh `/research --new` produces `RESEARCH-VIABILITY.md` with the three checks evaluated against the wiki-researcher brief. Verdict is rendered. `/research` blocks Step 7 entry until verdict is set.

## 3. P11.1b — Mechanism-Word Lock Gate (post first NLM ingestion)

**File to edit:** `D:\History vs Hype\.claude\commands\research.md` (`--apply-review` flow section, around line 488)

**Problem this solves:** P11.1a leaves the mechanism-word check pending because the NLM notebook isn't populated yet at Phase 1. After the user does first NLM ingestion via `--apply-review`, the notebook is populated and the mechanism-word check can finally fire against actual sources.

**Insertion point (validated):** Inside the `--apply-review` flow, after Step 5 ("Apply Approved Claims") completes for the first time. Detection logic: check whether `RESEARCH-VIABILITY.md` exists and contains pending mechanism-word candidates that haven't been resolved.

**Behavior the section must specify:**

1. **Trigger condition.** Fires automatically the first time `--apply-review` ingests claims into a project where `RESEARCH-VIABILITY.md` exists with mechanism-word candidates flagged for post-ingestion check.

2. **Single check: mechanism-word NLM-confidence.** For each mechanism-word candidate carried forward from P11.1a:
   - Run NotebookLM confidence query per existing `feedback-notebook-citation-grounding.md` scope-b rule.
   - Returns: HIGH / MEDIUM / LOW confidence per candidate.

3. **Verdict logic (per candidate):**
   - **LOCK** — Candidate returns HIGH confidence. Can proceed to title-stage with this mechanism word.
   - **SOFTEN** — Candidate returns MEDIUM. Either soften the language (e.g., "translation discrepancy" instead of "forged") OR acquire more sources to raise confidence. Re-check after source acquisition.
   - **SWAP** — Candidate returns LOW. Drop this candidate; try the next one on the list. If all candidates return LOW, escalate to user — this topic doesn't have a defensible mechanism, which may invalidate the original viability verdict.

4. **Output: append to `RESEARCH-VIABILITY.md`.** Section: "Mechanism-Word Lock Gate (post-NLM)". Lists each candidate, its NLM-confidence verdict, the chosen action (LOCK / SOFTEN / SWAP), and the locked mechanism word (or escalation note if none lock).

5. **Gate behavior.** Title locking (downstream — happens in `/script` or `/greenlight` final pass) cannot proceed until at least one mechanism-word candidate has LOCKED. If all SWAP'd, the topic re-enters viability assessment.

**Cross-reference at top of section:**
> "Post-NLM half of the viability gate (other half: P11.1a Topic Viability Gate, Phase 1). Required because mechanism-word grounding can only be checked against an actual NLM notebook, not against a Phase 1 brief. See `feedback-notebook-citation-grounding.md` §'mechanism claims' for the canonical NLM-confidence query."

**Acceptance:** After the edit, the first `--apply-review` call on a project with pending mechanism-word candidates produces the lock-gate output appended to `RESEARCH-VIABILITY.md`.

4. **Downstream consumption.** When `/script` starts, it reads this section. The writer (or `script-writer-v2` agent) picks from the candidates or explicitly rejects with reason.
